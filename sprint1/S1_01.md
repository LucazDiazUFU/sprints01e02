# S1_01 — Compreensão do problema

O Trabalho 1 propõe um sistema para registrar ativos de TI e as vulnerabilidades encontradas neles. Um ativo pode ser um computador, servidor, equipamento de rede ou outro recurso utilizado pela organização. A vulnerabilidade é uma falha ou condição que pode comprometer esse recurso. Antes de programar, preciso identificar quais dados serão guardados e quais operações o usuário poderá realizar.

O cadastro de um ativo deve permitir sua identificação por um ID, nome, tipo, responsável e localização. Também é útil registrar sua criticidade e situação. Para uma vulnerabilidade, são necessários pelo menos um identificador, descrição, grau de severidade, ativo relacionado e situação do tratamento. O ID evita confusão entre registros com nomes parecidos; a ligação ao ativo mostra onde o problema foi encontrado.

O usuário principal é a pessoa responsável por manter o inventário e acompanhar os riscos. Ela precisa cadastrar, consultar, alterar e remover registros. O sistema deve informar quando um campo obrigatório estiver vazio, quando um ID já existir ou quando a busca não encontrar um registro. Uma vulnerabilidade não deve apontar para um ativo inexistente.

Como primeira solução, os dados podem ficar em memória durante a execução dos exercícios. Depois, podem ser gravados em JSON para continuar disponíveis quando o programa fechar. A interface inicial será pelo terminal, com menus e mensagens simples. Essa divisão permite desenvolver cada parte e verificar o resultado antes de avançar.

## Exemplo aplicado

Um notebook de ID 101 é usado pelo setor administrativo. Durante uma verificação, foi encontrada uma versão desatualizada de software com grau 7. O usuário cadastra o notebook e, em seguida, registra a vulnerabilidade vinculada ao ID 101. Ao consultar o ativo, consegue identificar o responsável e o problema associado. Se tentar informar o ID 999, que não existe, o cadastro da vulnerabilidade deve ser recusado.

Os requisitos funcionais descrevem o que o programa faz, como cadastrar e consultar. Os não funcionais indicam condições de qualidade, como mensagens claras, organização do código e preservação dos dados. Os próximos exercícios detalham esses requisitos e os critérios usados para conferi-los.
